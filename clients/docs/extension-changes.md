## Behaviour that differs from upstream

- A login's custom field with a plain name ("Numéro fiscal") is typed into **one** control, the
  best label match, and never into a password box; upstream typed it into every control whose id,
  name, label or neighbouring text equalled the name. Names in Bitwarden's rule syntax (`id=…`,
  `name=…`, `label=…`, `placeholder=…`, `regex=…`, `csv=…`) and linked fields behave as upstream.
  Cards and identities are untouched.
- A login with a `taviri:recipe` (or `grokbot:recipe`) field is filled by its recipe on its own
  site, and is not filled at all by "autofill on page load".
- The recipe of a shared (organization) login is ignored and the login is filled the regular way:
  anyone who can edit a shared login could otherwise make the browser click things on that site
  (`SMARTFILL_RUN_ORGANIZATION_RECIPES` in `smartfill-recipe.background.ts`).
- TOTP in a recipe follows the same entitlement as upstream's TOTP fill (Premium, or an
  organization that uses TOTP).
- Item icons: a `taviri:icon` field changes the item's icon (pack icons show even with website
  icons turned off, since they come from the app itself); in a branded build, notes, SSH keys,
  cards, identities and logins without a website get the pack icon of their type instead of the
  font icon. Custom fields named `taviri:…` or `grokbot:…` hold settings and are never typed into
  pages (same rule as the Taviri connector).

## Tests

`npx jest --config libs/common/jest.config.js libs/common/src/vault/icon` from the repository root
for the item icons (25 new tests next to upstream's icon tests). End-to-end tests with a
local fake vault live outside this checkout, in `clients/extension/test` in the Taviri repository.
